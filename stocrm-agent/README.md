# STOCRM-агент — версия 80

Telegram-бот (текст и голос) и MCP-сервер. В этом комплекте только файлы для запуска: без тестов, старых отчётов, исходных вложений, ключей и виртуального окружения.

## Что запускать на Windows

1. **Остановите старого бота:** закройте его окно. Одновременно должна работать только одна копия.
2. Распакуйте архив целиком в **новую папку**. Не запускайте файлы внутри ZIP и не накладывайте их на старую установку.
3. При обновлении скопируйте из старой папки файл **`.env`** и всю папку **`.state`** в новую. Это ваши настройки, доступы, подтверждения и блокировки незавершённых операций. Не удаляйте `.state` ради повторной записи. Если пути к состоянию в `.env` абсолютные — сохраните доступ к указанным каталогам. Старую `.venv` не переносите.
4. Дважды щёлкните **`setup.bat`**. Мастер создаст окружение и установит зависимости. Существующие настройки не нужно вводить заново без необходимости. При первой установке заполните домен и ключ STOCRM, токен Telegram, свой Telegram ID, ключ Google AI Studio для модели и Groq для речи. Не отправляйте ключи в чат.
5. После завершения установки дважды щёлкните **`start_bot.bat`**. Держите это окно открытым — это работающий бот.

Если Python отсутствует, установите Python 3.12 или 3.13 с python.org, отметив **Add python.exe to PATH**, затем повторите `setup.bat`. Для установки зависимостей и работы внешних сервисов требуется интернет.

Для реальной CRM в `.env` должно быть **`STOCRM_MOCK=0`**, не `1`. В `/settings` оставьте подтверждение включённым. Ограничьте доступ к боту своими ID.

## Исправления версии 80

«Покажи сделки в просчёте» также ищет статус «Просчёт запчастей» в выбранной воронке. Бот дополнительно проверяет статусы и воронку возвращённых сделок; при нескольких подходящих статусах просит уточнить, при неполном чтении не объявляет список полным.

Краткая карточка показывает расчётный долг, когда сумма работ, стоимость товаров и оплата доступны и относятся к рублям; если входные данные или валюта не подтверждены, вместо долга указано, что остаток неизвестен. Его нужно сверить с панелью CRM.

**Заметки:** сохранение заметок через бота временно отключено, в том числе применение старых черновиков. Ранее API вернул ID заметки, но она не появилась в карточке. Документация не подтверждает, как привязать её к видимому блоку сделки; ответ API и наличие записи в API не доказывают отображение в панели. Поэтому бот больше не сообщает о надёжном успехе и не пытается записать заметку повторно. Заметка №623 не удалялась и не создавалась заново; её фактическое состояние неизвестно.

Всё проверено локально на имитации; отображение и состав ответов настоящей CRM ещё не проверены. Для новых проверок используйте отдельную тестовую сделку, не повторяйте неопределённые старые операции и сохраните `.state`.

## Запись клиента по телефону

Например: «Запиши клиента 8XXXXXXXXXX на завтра в 12 к Андрею». Бот проверяет контакт по полному телефону, включая дополнительные номера. Если телефон указан у нескольких контактов, сначала предложит выбрать клиента. На большой базе проверяются дополнительные телефоны не более 20 карточек за проход; при ошибке карточки или таком ограничении поиск неполон. Найденный по основному телефону контакт предлагается только для явного выбора с предупреждением; отсутствие совпадений при неполном поиске не позволяет создавать контакт. Только после полного поиска без совпадений бот спросит имя для нового контакта.

Бот проверяет сделки выбранного контакта. Активными считаются все, кроме статусов «Успешно реализовано», «Отказ», «Мусор», «Возврат». Если активные сделки есть, выберите **создать новую** или одну из показанных существующих. При существующей сделке бот отдельно спросит, менять ли её статус; после этого уточнит недостающие время, длительность или пост. Если активных сделок нет, бот сначала предложит явно выбрать создание новой сделки. Перед каждой записью отдельно подтверждается длительность: кнопками «1 час» или «Своя длительность»; если время уже задано в команде, его тоже можно подтвердить. При выборе своей длительности укажите, например, «45 минут» или «до 10:30». Один черновик объединяет сделку и запись в календарь; при включённом подтверждении до его нажатия изменения не записываются.

Бот не берёт сделку из предыдущего разговора для другого клиента по телефону. Если сделки не удалось достоверно проверить, запись не начинается; при неполном поиске контактов допустим только явно выбранный найденный контакт, без автоматического создания нового. Перед подтверждением сведения проверяются повторно; если они изменились, выбор нужно сделать заново. Сохранённые незавершённые/неопределённые попытки блокируют повтор, проверяйте их в CRM и `/drafts`.

Старые неподтверждённые черновики записи в календарь из предыдущих версий без новой проверки клиента **блокируются**. Если вы уверены, что черновик ещё не отправлялся, отмените его и подготовьте заново. Если результат неизвестен или статус `partial`, не повторяйте команду и не удаляйте состояние: сначала проверьте CRM.

## Цветные статусы сделок

В списках сделок и карточке бот показывает цветной значок рядом со статусом. Цвет берётся из справочника текущей воронки STOCRM (`FRONT_COLOR`), в том числе для «Просчёта», «Записи» и «В работе», а не назначается по названию. Изменение цвета или статуса в панели может появиться после обновления кэша справочника (до 10 минут). При ответе, составленном моделью, цвет может выводиться отдельным списком для явно названных сделок.

В Telegram нельзя окрасить произвольным цветом текст или карточку, поэтому значок — **приблизительный** цвет из ограниченного набора эмодзи; близкие оттенки могут выглядеть одинаково. Название статуса сохраняется. Если CRM не вернула цвет, статус не найден или справочник недоступен, бот покажет статус без выдуманного значка. Проверить: «Покажи последние сделки», затем «2 подробнее»; сопоставьте значок с цветом этой сделки в панели.

## Несколько товаров и выбор бренда — версия 78

Например: «Добавь в сделку НОМЕР товары CH88011 за 1200 и CH88014E за 4200». Бот сохраняет для каждой строки её артикул, цену продажи и количество. Если сделка не названа и недавняя сделка неизвестна, спросит номер. Если для артикула есть неоднозначные варианты, выберите нужный; первый в списке — наиболее подходящий по доступным данным, но **не гарантия применяемости**. Для интернет-вариантов показываются источники. Если точного варианта нет, можно указать бренд, выбрать «Добавить как указано», пропустить позицию или отменить заявку. Неизвестный бренд обозначается в CRM техническим NONAME, а не считается найденным производителем.

Пока вопросы по заявке не завершены, позиции **не записываются** и кнопка подтверждения не показывается. Затем создаётся один общий черновик с одной кнопкой подтверждения. Если подтверждение отключено в `/settings`, запись начинается только после всех ответов. Очередь отправляет позиции по одной и проверяет каждую в CRM; при ошибке или несоответствии останавливается. Пакетный диалог хранится в памяти: после перезапуска незавершённые вопросы придётся начать заново; незавершённые/partial записи в `.state` сохраняют защиту от повтора, в том числе при новой команде или изменении бренда. Удаление из основного списка не снимает блокировку; такие попытки доступны для проверки через `/drafts`.

Для неизвестных артикулов поиск по возможности объединяет до четырёх номеров в один запрос **к одному выбранному поисковику**. Выдача может содержать не все товары; найденный бренд предлагается только при связи с точным артикулом в том же фрагменте выдачи. Кэш, ограничение частоты и пауза после CAPTCHA/429 снижают нагрузку; обхода блокировок и гарантии полноты нет. Маршрут сети может проверяться отдельно. Поиск по отдельной позиции и другие функции могут делать собственные запросы. Если нужен заказ у поставщика или учёт закупочной цены для нескольких позиций, пока отправляйте их **отдельными запросами** с поставщиком и закупочной ценой: бот не подменяет такой заказ свободной позицией.

## Исправление сообщения об остатке склада — версия 79

Остаток виртуального склада не является количеством товара в сделке. Бот больше не берёт количество из вложенного `FORMATTED_STOCK` в итоговом сообщении и не считает большое число ошибкой само по себе. При контрольном чтении приоритет у поля строки `QUANTITY_CURRENT`, если оно присутствует. Если неоднозначное количество не совпало с ожидаемым и поле строки отсутствует, бот сообщает, что количество **не удалось надёжно проверить**, останавливает очередь и защищает от повтора. Это не утверждение, что количество в сделке неверно. Старые `partial` и предупреждения сохраняются; не удаляйте `.state` и не добавляйте товар повторно без проверки в CRM.

Эти проверки выполнены на имитации API. Реальный ответ для сделки 1313 не изучен, текущее количество строки 8297 не установлено. Склад и CRM не изменялись.

## Как проверить добавление позиции

Используйте **новую тестовую сделку**. Не повторяйте старые неопределённые или partial-операции (в частности, прежнюю попытку по сделке 1313 / заявке 8517).

1. Отправьте боту, заменив `НОМЕР` на номер тестовой сделки:
   **«Добавь в сделку НОМЕР товар DAP, артикул 2430TK1204, бренд DAP, количество 2, цена продажи 500 рублей за штуку».**
   Это искусственная тестовая цена, не рекомендация цены товара.
2. Проверьте черновик: нужная сделка, бренд DAP, артикул 2430TK1204, 2 штуки, по 500 рублей. До подтверждения записи быть не должно. Если бот спрашивает изменение статуса существующей сделки, выберите сохранение статуса.
3. Подтвердите **один раз**. Для нескольких позиций одной команды должно быть одно подтверждение всей пачки.
4. Откройте сделку в STOCRM и сверьте артикул, бренд, количество **2**, цену **500 за штуку**, сумму **1000**, отсутствие дубля. Сообщения «запрос принят» недостаточно — важна фактическая строка в панели.
5. Если бот сообщает `partial`, неопределённый результат или несовпадение цены/количества: **не повторяйте команду и не подтверждайте повторно**. Сначала проверьте сделку и заявку в панели, затем соберите диагностику.

Версия 75 использует `offer/order/add_free_order` как основной метод обычного ручного добавления. Подбор склада и поставщика для него не нужен. После ответа API бот перечитывает строку и проверяет цену/количество; при несовпадении или неоднозначном количестве останавливает пачку без автоматического повторного добавления и без переключения на другой метод.

Неподтверждённый старый ручной черновик со старым маршрутом записи блокируется. Создать новый вместо него можно только если попытки записи ещё не было; `partial` и уже отправленные заявки таким способом обходить нельзя.

## Проверка даты записи — исправление версии 75

Если бот уже знает «сегодня» и спрашивает время, ответы **«11 утра»**, **«11»**, **«в 11»**, **«11:00»** сохраняют выбранную дату и означают 11:00. Чтобы явно поменять день месяца, напишите «11 ноября» или «11 числа».

Проверка на тестовой сделке: «Запиши сделку НОМЕР на сегодня к рыжему» → ответьте на вопрос о статусе → «11 утра» → «час». В черновике должна быть сегодняшняя дата, интервал 11:00–12:00. При включённых подтверждениях до нажатия подтверждения запись не создаётся.

Ранее ошибочно созданная запись №2153 сама не переносилась. Сначала проверьте её текущее состояние в панели; если она всё ещё на неверной дате, исправляйте именно эту запись, не создавая дубль. Обновление меняет понимание новых ответов, а не существующие данные CRM.

## Если возникла проблема

Дважды щёлкните **`collect_report.bat`**. Он не изменяет CRM, создаёт диагностический `support_report.txt` и открывает его в Блокноте. Укажите текст команды, ответ бота и номер тестовой сделки. Перед отправкой просмотрите файл и удалите личные сведения. Не присылайте `.env`, токены, SID или всю `.state`.

В отчёте версия кода должна быть **80**, дата **2026-10-31**. Иначе запущена другая папка или старая копия.
