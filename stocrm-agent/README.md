# STOCRM-агент — версия 107

Telegram-бот (текст и голос) и MCP-сервер. В этом комплекте только файлы для запуска: без тестов, старых отчётов, исходных вложений, ключей и виртуального окружения.

## Что запускать на Windows

1. **Остановите старого бота:** закройте его окно. Одновременно должна работать только одна копия.
2. Распакуйте архив целиком в **новую папку**. Не запускайте файлы внутри ZIP и не накладывайте их на старую установку.
3. При обновлении скопируйте из старой папки файл **`.env`** и всю папку **`.state`** в новую. Это ваши настройки, доступы, подтверждения и блокировки незавершённых операций. Не удаляйте `.state` ради повторной записи. Если пути к состоянию в `.env` абсолютные — сохраните доступ к указанным каталогам. Старую `.venv` не переносите.
4. Дважды щёлкните **`setup.bat`**. Мастер создаст окружение и установит зависимости. Существующие настройки не нужно вводить заново без необходимости. При первой установке заполните домен и ключ STOCRM, токен Telegram, свой Telegram ID, ключ Google AI Studio для модели и Groq для речи. Не отправляйте ключи в чат.
5. После завершения установки дважды щёлкните **`start_bot.bat`**. Держите это окно открытым — это работающий бот.

Если Python отсутствует, установите Python 3.12 или 3.13 с python.org, отметив **Add python.exe to PATH**, затем повторите `setup.bat`. Для установки зависимостей и работы внешних сервисов требуется интернет.

Для реальной CRM в `.env` должно быть **`STOCRM_MOCK=0`**, не `1`. В `/settings` оставьте подтверждение включённым. Ограничьте доступ к боту своими ID.

## Просмотр статусов при отсутствии ID — версия 107

Если CRM не возвращает поле `STATUS_ID` в строке сделки, списки по статусам и просмотр быстрых сделок могут сверить название сделки с единственным одноимённым статусом этой воронки в справочнике (учитываются и неактивные статусы). Воронка, номер сделки и, для карточки быстрой сделки, её контакт проверяются отдельно. При неоднозначности, отсутствии названия или несоответствии фактически полученного ID подстановка не выполняется. Бот отмечает, что статус сверялся по названию и это только просмотр; такие данные не доказывают ID статуса. Карточка при выборе перечитывается. Списки могут оставаться неполными.

Правила записи и подтверждения остались строгими: название не заменяет ID в быстрой сделке, старые частичные заявки не продолжаются и не разблокируются. Это исправление просмотра, а не исправление добавления товаров и услуг. Проверено на имитации, работа с реальной CRM не проверена.

## Диагностика ID статуса — версия 106

Администратор может использовать `/offer_test НОМЕР`, чтобы узнать, отсутствует ли поле ID статуса или присутствует в другом формате. Команда также сравнивает название статуса сделки с однозначным активным названием «Быстрые сделки» из справочника. Это только диагностика: совпадение названий не подтверждает ID и не разрешает запись. Сырые данные и сведения о клиенте не выводятся. Проверка и блокировки записи не ослаблены; старые заявки не продолжаются. Поведение на реальной CRM не проверено.

## Ожидание оплаты и диагностика сделки — версия 105

«Покажи сделки в ожидании оплаты» и «покажи сделки которые ожидают оплаты» ищут точный подходящий статус в CRM, а не все неоплаченные сделки. Если подходящих статусов несколько, бот попросит уточнить; дополнительные условия не отбрасываются. Это только чтение.

Администратор может отправить `/offer_test 1335` с нужным номером: бот повторно прочитает сделку и покажет, получены ли идентификаторы, в том числе ID статуса. Команда не выводит имя, телефон, ключи или сырое содержимое ответа, не меняет CRM и не снимает блокировку. Вместе с `/balance_test` это поможет понять, какие поля фактически возвращает панель; успех работы новой записи не гарантируется.

После подтверждения быстрая сделка уже выполняется последовательно отдельными запросами: создание, смена статуса, работа, искомая запчасть, свободная позиция, с проверками после шагов. Если обязательный ID не подтвердился, дальнейшие запросы не отправляются. Убирать непроверенную заявку из списка не значит отменить записи или снять блокировку. Не повторяйте и не возобновляйте старые заявки автоматически; сохраните `.state` и проверьте каждый этап в CRM.

## Список статуса и диагностика баланса — версия 104

«Покажи быстрые сделки» — чтение всех подтверждённых сделок в точном статусе «Быстрые сделки», независимо от контакта. У каждой карточки проверяются её номер, контакт, воронка и статус; позиции и оплаты другой сделки не подставляются. Непроверенные строки не объявляются отсутствующими: список предупреждает о возможной неполноте. До 10 карточек и кнопки выбора; точный активный статус должен быть однозначен. Это только чтение. При создании или дополнении быстрой сделки по-прежнему используется исключительно системный контакт, а запись выполняется после подтверждения.

Бот явно запрашивает идентификаторы сделки и поля карточки через `REQUIRED_FIELDS` (Public API WIKI-A-593/595). Это может помочь, если панель не включает поля по умолчанию, но причина конкретных ответов пользователя пока не установлена. Долг считается только при проверенных суммах и совпадающих ID и типе сущности в ответе баланса; если данные не подтверждены, он остаётся неизвестным, не нулём. Чтобы выяснить, почему баланс не читается, администратор может отправить `/balance_test 1334` с нужным номером сделки. Это только чтение: результат содержит тип ответа и счётчики проверки, без суммы, содержимого ответа, личных данных и ключей. Тексты ошибок API не выводятся.

Все проверки — на имитациях; реальный ответ STOCRM неизвестен и совместимость не гарантируется. Сохраните `.state`, не повторяйте и не разблокируйте частично выполненную заявку без проверки в CRM. Версия не продолжает старые записи автоматически.

## Проверка статуса после создания — версия 103

После создания быстрой сделки и отправки смены статуса бот при несовпадении до трёх раз повторяет только контрольное чтение, с паузами 0,5, 1 и 2 секунды. Создание сделки, смена статуса и добавление позиций автоматически не повторяются. Каждая проверка заново подтверждает системный контакт, воронку, статус и саму сделку. Если совпадение не подтверждено, дальнейших записей нет, сохраняются частичный результат и блокировка. Предупреждение теперь различает отсутствие сделки в ответе и несовпадение ID. Успешное первое чтение не добавляет пауз.

Команды списков по статусу обрабатываются до незавершённых диалогов и модели, с проверкой точного статуса. Причина конкретного прежнего смешанного списка пока не установлена. Проверки выполнены только на имитации: задержка чтения — возможное, но не доказанное объяснение остановки в реальной панели. Само изменение не продолжает и не исправляет старую частичную заявку. Сохраните `.state`, не повторяйте и не разблокируйте заявку без ручной проверки CRM. Ответы реальной CRM и формат добавления товара могут отличаться от имитации.

## Проверка и ускорение — версия 102

Явная команда «новая быстрая сделка» больше не читает список существующих сделок перед созданием черновика. Контакт и статус по-прежнему перепроверяются, в том числе перед записью. Несколько карточек быстрых сделок читаются максимум по две одновременно; порядок и предупреждения о недоступном долге сохраняются. Поиск деталей не сбрасывается только из-за проверки справочника быстрых сделок. Запись и проверки после неё намеренно не ускоряются за счёт пропуска проверок или повторных записей.

Мастер установки проверяет импорты, диапазоны версий и конфликты зависимостей. Для автоматической установки проверка TLS не отключается: при ошибке сертификата проверьте системное время, доверенные сертификаты и настройки прокси. Диапазоны пакетов ограничены; это не гарантия совместимости будущих версий.

Проверено локально на Python 3.11, имитациях CRM и Telegram с MCP 1.30 и 2.3. Для Windows/Python 3.12 и 3.13 проверен только подбор бинарных пакетов, не запуск на Windows. В тестовой имитации подготовка новой сделки использовала 10 обращений к CRM вместо 12; четыре искусственно задержанные карточки читались за 0,16 вместо 0,32 секунды. Это не измерение вашей реальной сети: время и ограничения зависят от CRM и подключения. Полное отсутствие ошибок и совместимость с живыми API не гарантируются.

## Быстрые сделки — версия 101

Примеры:

- «**быстрая сделка прокачка тормозов 1000 рублей**»;
- «**новая быстрая сделка прокачка тормозов 1000 рублей и добавь артикул CR9E цена 300**»;
- «**покажи быстрые сделки**».

При создании и добавлении позиций используется только существующий системный контакт **1111 быстрые сделки**, телефон-заглушка **81111111110**. Просмотр статуса с версии 104 охватывает все контакты. Имя и телефон, точный активный статус «Быстрые сделки» и его воронка ищутся в CRM, ID не зашиты. Если они не подтверждены однозначно или поиск неполный, бот остановится. Если у перехода несколько причин, выберите нужную кнопкой.

Без слова «новая» при наличии быстрых сделок бот предложит выбрать существующую или создать новую; при отсутствии — подготовит новую. Слово «новая» сразу означает создание новой. В выборе показаны работы, товары и долг, если данные удалось прочитать. Кнопки привязаны к сотруднику и устаревают; при изменении списка нужно выбрать заново. На экране до 10 сделок; если их больше, показано ограничение, а нужную можно указать так: «быстрая сделка №123 диагностика 1000 рублей».

Работа и артикулы сохраняются в **один черновик**: до кнопки «Применить» записей нет, независимо от режима `/settings`. Каждую неназванную цену бот спрашивает отдельно; ноль не подставляется. Укажите бренд явно, например «бренд NGK». Если он не назван, бот ищет точный артикул в доступных источниках; при нескольких вариантах предлагает выбор, а если бренд не подтверждён — просит ввести его вручную. **NONAME автоматически не подставляется**. Недоступный или неполный источник не доказывает отсутствия товара. Запчасть добавляется только свободной позицией, без заказа поставщику. Другие действия и несколько работ в одной фразе пока не разбираются: повторите запрос отдельными действиями, не полагайтесь на догадки.

В готовом черновике кнопками ✂️ можно удалить отдельную работу или товар до подтверждения. Остальные строки сохраняются; удаление последней строки отменяет черновик. После удаления проверьте новый состав и подтвердите его новой кнопкой: старые кнопки больше не действуют. Уже применяемые или частично выполненные заявки менять нельзя. Ранее подготовленный черновик с NONAME не применится: если запись ещё не отправлялась, отмените его и подготовьте заново с брендом. Если запись могла быть отправлена, сначала проверьте CRM и `/drafts`, не повторяйте её вслепую.

После подтверждения сделка, контакт, статус, работа и позиции проверяются чтением. При потере ответа, несовпадении или неполной проверке цепочка останавливается, сообщает известные номера и выполненные шаги; старый черновик **не повторяется**. Проверьте CRM и `/drafts`. Только после ручной проверки администратор может подтвердить снятие блокировки для будущих заявок; это **не повторяет** старую операцию. Если процесс был прерван в статусе «выполняется», возможность ручной проверки появляется после часа без обновлений. Не удаляйте `.state`.

Проверено на имитациях CRM и Telegram, без запросов в рабочую CRM. Для первого применения проверьте в CRM существование контакта и статуса; поведение реальной панели и доступ API не подтверждены. Если CRM не возвращает привязку искомого артикула к сделке или ID новой строки, бот остановится с частичным результатом, а не станет считать запись подтверждённой.

## Списки сделок по статусам — версия 99

Бот различает **«сделки в записи»**, **«в заказе»**, **«в просчёте»**, **«в работе»** и **«собранные заказы»**. Это разные статусы, не список всех активных сделок и не взаимозаменяемые понятия. Названия и идентификаторы берутся из справочника CRM, каждая строка проверяется по воронке и статусу. Например, статус «Заказ» не включает «Заказ собран»; просчёт запчастей не смешивается с другими похожими статусами.

Если есть несколько подходящих статусов или воронок, бот попросит уточнить. Для любого другого статуса можно назвать его **точно как в CRM**, например: «покажи сделки в статусе Успешно» или «покажи сделки в статусе Заказ в воронке Автосервис». Если бот не узнаёт название, он попросит уточнение, а не покажет общие активные сделки. Сочетание нескольких статусов или дополнительного условия, например клиента или даты, в этих коротких запросах пока не поддерживается: бот попросит разделить запросы.

Это только чтение, не изменение статуса и не создание заказа. Проверяются до пяти страниц, показывается до 25 строк; при ограничении или ошибке выдаётся предупреждение. Исправление проверено на имитации CRM, реальные названия статусов и поведение фильтров в вашей базе ещё нужно проверить.

## Сделки в работе на сервисе — версия 98

Фразы **«покажи сделки в работе»**, «какие сделки в работе» и «что в работе» означают сделки в статусе **«В работе на сервисе»**, а не все активные сделки. Бот читает справочник воронок и статусов CRM, ищет точное название и запрашивает соответствующие сделки. Если такого названия нет, он использует точный статус «В работе» и показывает название воронки и статуса в ответе; ID не зашиты в код. Данные сделок перечитываются при каждом таком запросе.

Если подходящий статус есть в нескольких воронках, бот попросит уточнить воронку, например «покажи сделки в работе в воронке Автосервис». При сбое чтения, неполном ответе, повторе страниц или ограничении списка бот предупреждает, а не показывает все активные сделки как нужную выборку. Вывод ограничен 25 позициями, проверка — пятью страницами. Команда только читает CRM и ничего не меняет. Нажатие кнопок или повторение старых неопределённых записей не требуется.

Проверено на имитации CRM; названия статусов и работу серверного фильтра в вашей живой базе ещё нужно проверить. Если названия отличаются, бот не угадает статус — он попросит проверить название.

## Подробный локальный ответ Профит Лиги — версия 97

Раньше `/parts_test` показывал только краткую ошибку, например HTTP-статус; развёрнутого ответа Профит Лиги не было. Теперь при ошибке сетевого поиска, HTTP-отказе, неожиданном формате или неполном ответе бот сохраняет отдельный файл **только на вашем компьютере** в `profit_liga_local_reports` рядом с используемым `.env`. Если `.env` не найден, папка создаётся в рабочей папке бота. В `/parts_test` появляется краткая ошибка и сообщение о сохранении; если сохранить файл не удалось, бот сообщает об этом.

Чтобы открыть папку, дважды щёлкните **`Открыть_отчёты_Профит_Лиги.bat`** и откройте свежий `profit-liga-error-...txt` в Блокноте. В файле: HTTP-статус, Content-Type, тип и подробности сетевой ошибки, полученное тело ответа (до 2 МБ) и отметка, если оно прервано или ограничено. Тело может включать и другие данные поставщика; они не используются при подборе или заказе. Каждый отчёт создаётся отдельно. При успешном или пустом корректном ответе файл не создаётся; при выключенном поиске, отсутствующем ключе или некорректном артикуле сетевой запрос и отчёт не создаются.

**Не отправляйте файл целиком без проверки.** Он может содержать личные сведения, секреты или фрагменты ключа. Известный ключ и некоторые его представления маскируются по возможности, но это не гарантирует безопасность. Никогда не отправляйте `.env`, ключ или URL запроса. Если нужна помощь, просмотрите ответ локально и передайте только обезличенное описание ошибки. Папка исключена из Git, но это не защита от резервных копий и других программ; отчёты можно удалить вручную.

Для отчёта используется тот же единственный запрос поиска — без повторного обращения, перенаправления, заказа или изменения CRM, `.env` и `.state`. Проверено только на локальных имитациях; работу с реальным API и Windows необходимо проверить на вашем компьютере.

## Поиск брендов Профит Лиги — версия 96

По умолчанию выключен. Для подключения остановите бота и запустите **`Настроить_Профит_Лигу.bat`** в папке бота. Введите существующий API-ключ **только в этом локальном окне**: ввод виден на экране. Бренды ищутся также при совпадении в CRM, различные бренды предлагаются для выбора. Результаты Росско не гарантируют применяемость запчасти.

**Безопасность:** программный клиент Росско не содержит операции заказа; модель не получает функцию произвольного вызова API Росско. Также во всём боте заблокированы заказы поставщикам через STOCRM, включая старые черновики с `offer/order/add` или запасными вариантами: это ограничение распространяется на всех поставщиков. При добавлении позиции используется только свободная строка `offer/order/add_free_order` без полей поставщика или склада; данные Росско для цены и количества не используются. Частично выполненные/неопределённые черновики не повторяйте и `.state` не удаляйте. Абсолютный запрет заказа на стороне Росско не доказан: эти ключи могут иметь права на заказы, а внешнее ПО, компрометация компьютера или ошибка поставщика находятся вне контроля бота. Этот модуль не запускается как изолированный процесс, системные права сети не ограничивает. Защищайте компьютер и `.env`; не отправляйте ключи в чат, модели, отчётах, скриншотах или кому-либо ещё.

### Локальная настройка без поддержки

1. Сохраните существующие `.env` и `.state` при обновлении, как написано выше. Не пересоздавайте ключи, если это может отключить действующую интеграцию STOCRM.
2. В личном кабинете Росско найдите **уже имеющиеся** ключи API `KEY1`, `KEY2`. Если понадобятся ID, их нужно найти для своего аккаунта. Документация GetSearch требует `delivery_id`; при доставке не самовывозом нужен также `address_id`. Значения из документации — примеры, не используйте их как значения своего аккаунта. Где посмотреть конкретные ID в вашей панели, пока не подтверждено; не угадывайте их. При необходимости можно показать скриншот экрана настроек, предварительно скрыв все ключи, персональные данные и адреса.
3. Откройте свой `.env` локально, добавьте строки ниже и укажите значения **только на своём компьютере** (не в чате):

```
ROSSKO_ENABLED=1
ROSSKO_KEY1=ваш_ключ_1
ROSSKO_KEY2=ваш_ключ_2
ROSSKO_DELIVERY_ID=
ROSSKO_ADDRESS_ID=
```

Для пробного поиска без ID оставьте обе последние строки пустыми. По документации ID доставки обязателен, поэтому запрос может быть отклонён. Перезапустите бота. Для отключения верните `ROSSKO_ENABLED=0`. Ключи и настройки должны быть доступны только владельцу компьютера. Подключение использует прямой выход в сеть без системного прокси, и из некоторых сетей может не работать.
4. Отправьте `/parts_test 2DUF050N7`: строка «Росско» покажет, найден ли точный бренд, источник недоступен или поиск отключён. Эта команда ничего не заказывает и не изменяет CRM. Только после успешной настройки проверяйте обычный поиск и, если нужно, подготовку **свободной** позиции; перед подтверждением сверяйте сделку, артикул, бренд, количество и вашу цену.

Все проверки версии 85 сделаны на имитациях, без вызова API Росско и без записей в настоящую CRM; реальное подключение и формат ответа аккаунта пользователя пока не проверены. Тестовый режим заказов Росско не требуется и не использовался.

## Склад как справочный источник — версия 84

Поиск запчастей снова проверяет склад, наряду с номенклатурой и историей. Он делает только чтение: складские идентификаторы не переносятся в заявку, команды списания и резервирования не отправляются. Для позиции, найденной только на складе, бот сначала предлагает выбор. Цену закупки или продажи со склада и остаток бот автоматически в сделку не подставляет; если позиция найдена только на складе и цена не названа, её нужно указать.

Остаток отдельной складской строки показывается только справочно. Он может относиться к виртуальному складу и **не является количеством в сделке или гарантией фактического наличия**. Если совпадение уже найдено в панели, интернет-поиск может не запускаться.

Команда `/parts_test АРТИКУЛ` показывает результат проверки склада, истории, номенклатуры и причину пропуска интернета. Она только читает данные. Реальная CRM и внутреннее поведение склада здесь не проверялись: испытания выполнены на имитации. Не повторяйте старые неопределённые операции и не удаляйте `.state`.

## Поиск запчастей — версия 83

Если производитель назван явно, например «производитель FEHU, артикул FRC 1012», бот сохраняет указанное человеком название даже при разделении запятыми и не представляет его как проверку в интернете. Если не названа сделка или цена, бот спросит их; до нужных ответов запись не выполняется. У нескольких позиций производители и цены не переносятся автоматически между артикулами.

Поиск по артикулу пропускает финансовые и другие нерелевантные результаты; нужны признаки запчасти и связь бренда с точным артикулом. Пробелы и дефисы в артикуле сопоставляются, но другие цифры и буквы не подменяются. Найденные бренды показываются для выбора со ссылками: например, по 2DUF050N7 возможны разные производители, поэтому один не назначается автоматически. Поиск использует один запрос выбранному провайдеру, учитывает ограничения и не обходит блокировки. Недоступный поиск отличается от выдачи без подтверждённого бренда; ни то ни другое не означает, что товара нет. Фильтрация может пропустить реальные товары, если фрагменты поиска недостаточно информативны. Наличие, применяемость и доступность поставки нужно проверять отдельно.

Проверки выполнены на имитации поисковой выдачи и CRM; реальный поиск с вашего компьютера, голос и рабочая CRM не проверялись.

## Добавление клиента — версия 82

Команда «Добавь клиента ТЕЛЕФОН» запускает создание контакта, а не поиск товара по номеру. Если имя не указано, бот спросит его; напишите сначала имя, затем фамилию и отчество, если известны. Можно указать имя и телефон сразу. Бот не выдумывает недостающие данные; если телефон не указан, спросит его. Для отмены напишите «отмена» или выполните `/reset`.

Перед подготовкой бот проверяет существующие основные и дополнительные телефоны. При совпадении сообщает найденных клиентов и не создаёт дубль. Перед применением поиск повторяется. При включённом подтверждении появляется черновик с именем и телефоном; при отключённом действует политика `/settings`.

Бот перечитывает контакт по полученному ID и проверяет имя и телефон; неясный ответ, ошибка контрольного чтения или обрыв связи оставляет операцию `partial` и блокирует повтор для того же телефона. При таком результате проверьте CRM и `/drafts`; не повторяйте вслепую и не удаляйте `.state`. Полностью исключить одновременное создание контакта в панели после последней проверки API нельзя. Старые черновики с телефоном без проверки блокируются; отменять их и создавать новый можно только если запись ещё не отправлялась.

## Голос, услуги и поиск бренда — версия 81

Фрагмент «в сделку 13.25» после распознавания трактуется как номер **1325**, а «сделку подробно 13.14» — как **1314**. Точки в ценах и другие числа так не меняются. Если слово «сделка» распознано совсем неразборчиво (например, «и ЛК 1325»), бот попросит повторить, не подставляя предыдущую сделку. Если голосовое распознано неверно, исправьте команду текстом и проверьте номер перед подтверждением.

Если вместе названы и услуги, и товары, бот попросит отправить их отдельно, чтобы не потерять позицию. Цена или название, которые невозможно уверенно разделить, требуют уточнения.

Первый запрос больше не ограничивается прогревом сети: запускается сам поиск. Бренды показываются с источниками для выбора; похожие артикулы и наличие в поисковой выдаче не подтверждают применяемость. Исправленный артикул можно сообщить текстом в ответ на вопрос о детали. Поиск может быть недоступен из-за настроек, сети или ограничений поисковика; это не доказывает отсутствие детали. Для пакетного поиска сохранены ограничения частоты и запрет обхода блокировок.

Доработан словарь-подсказка распознавания речи по умолчанию. Если в `.env` задан свой `STT_PROMPT`, используется он. Ни один механизм распознавания не гарантирует правильную транскрипцию: аудио со скриншотов и работа настоящих поисковиков здесь не проверялись.

## Запись клиента по телефону

Например: «Запиши клиента 8XXXXXXXXXX на завтра в 12 к Андрею». Бот проверяет контакт по полному телефону, включая дополнительные номера. Если телефон указан у нескольких контактов, сначала предложит выбрать клиента. На большой базе проверяются дополнительные телефоны не более 20 карточек за проход; при ошибке карточки или таком ограничении поиск неполон. Найденный по основному телефону контакт предлагается только для явного выбора с предупреждением; отсутствие совпадений при неполном поиске не позволяет создавать контакт. Только после полного поиска без совпадений бот спросит имя для нового контакта.

Бот проверяет сделки выбранного контакта. Активными считаются все, кроме статусов «Успешно реализовано», «Отказ», «Мусор», «Возврат». Если активные сделки есть, выберите **создать новую** или одну из показанных существующих. При существующей сделке бот отдельно спросит, менять ли её статус; после этого уточнит недостающие время, длительность или пост. Если активных сделок нет, бот сначала предложит явно выбрать создание новой сделки. Перед каждой записью отдельно подтверждается длительность: кнопками «1 час» или «Своя длительность»; если время уже задано в команде, его тоже можно подтвердить. При выборе своей длительности укажите, например, «45 минут» или «до 10:30». Один черновик объединяет сделку и запись в календарь; при включённом подтверждении до его нажатия изменения не записываются.

Бот не берёт сделку из предыдущего разговора для другого клиента по телефону. Если сделки не удалось достоверно проверить, запись не начинается; при неполном поиске контактов допустим только явно выбранный найденный контакт, без автоматического создания нового. Перед подтверждением сведения проверяются повторно; если они изменились, выбор нужно сделать заново. Сохранённые незавершённые/неопределённые попытки блокируют повтор, проверяйте их в CRM и `/drafts`.

Старые неподтверждённые черновики записи в календарь из предыдущих версий без новой проверки клиента **блокируются**. Если вы уверены, что черновик ещё не отправлялся, отмените его и подготовьте заново. Если результат неизвестен или статус `partial`, не повторяйте команду и не удаляйте состояние: сначала проверьте CRM.

## Цветные статусы сделок

В списках сделок и карточке бот показывает цветной значок рядом со статусом. Цвет берётся из справочника текущей воронки STOCRM (`FRONT_COLOR`), в том числе для «Просчёта», «Записи» и «В работе», а не назначается по названию. Изменение цвета или статуса в панели может появиться после обновления кэша справочника (до 10 минут). При ответе, составленном моделью, цвет может выводиться отдельным списком для явно названных сделок.

В Telegram нельзя окрасить произвольным цветом текст или карточку, поэтому значок — **приблизительный** цвет из ограниченного набора эмодзи; близкие оттенки могут выглядеть одинаково. Название статуса сохраняется. Если CRM не вернула цвет, статус не найден или справочник недоступен, бот покажет статус без выдуманного значка. Проверить: «Покажи последние сделки», затем «2 подробнее»; сопоставьте значок с цветом этой сделки в панели.

## Несколько товаров и выбор бренда — версия 78

Например: «Добавь в сделку НОМЕР товары CH88011 за 1200 и CH88014E за 4200». Бот сохраняет для каждой строки её артикул, цену продажи и количество. Если сделка не названа и недавняя сделка неизвестна, спросит номер. Если для артикула есть неоднозначные варианты, выберите нужный; первый в списке — наиболее подходящий по доступным данным, но **не гарантия применяемости**. Для интернет-вариантов показываются источники. Если точного варианта нет, можно указать бренд, выбрать «Добавить как указано», пропустить позицию или отменить заявку. Если бренд не подтверждён, введите его вручную: автоматически NONAME не подставляется. Нельзя сделать вывод об отсутствии товара, если поиск неполон или источники недоступны.

Пока вопросы по заявке не завершены, позиции **не записываются** и кнопка подтверждения не показывается. Затем создаётся один общий черновик с одной кнопкой подтверждения. Если подтверждение отключено в `/settings`, запись начинается только после всех ответов. Очередь отправляет позиции по одной и проверяет каждую в CRM; при ошибке или несоответствии останавливается. Пакетный диалог хранится в памяти: после перезапуска незавершённые вопросы придётся начать заново; незавершённые/partial записи в `.state` сохраняют защиту от повтора, в том числе при новой команде или изменении бренда. Удаление из основного списка не снимает блокировку; такие попытки доступны для проверки через `/drafts`.

Для неизвестных артикулов поиск по возможности объединяет до четырёх номеров в один запрос **к одному выбранному поисковику**. Выдача может содержать не все товары; найденный бренд предлагается только при связи с точным артикулом в том же фрагменте выдачи. Кэш, ограничение частоты и пауза после CAPTCHA/429 снижают нагрузку; обхода блокировок и гарантии полноты нет. Маршрут сети может проверяться отдельно. Поиск по отдельной позиции и другие функции могут делать собственные запросы. Заказы поставщикам и учёт закупочной цены через бота теперь заблокированы, в том числе для одиночных позиций; бот не подменяет такой заказ свободной позицией.

## Исправление сообщения об остатке склада — версия 79

Остаток виртуального склада не является количеством товара в сделке. Бот больше не берёт количество из вложенного `FORMATTED_STOCK` в итоговом сообщении и не считает большое число ошибкой само по себе. При контрольном чтении приоритет у поля строки `QUANTITY_CURRENT`, если оно присутствует. Если неоднозначное количество не совпало с ожидаемым и поле строки отсутствует, бот сообщает, что количество **не удалось надёжно проверить**, останавливает очередь и защищает от повтора. Это не утверждение, что количество в сделке неверно. Старые `partial` и предупреждения сохраняются; не удаляйте `.state` и не добавляйте товар повторно без проверки в CRM.

Эти проверки выполнены на имитации API. Реальный ответ для сделки 1313 не изучен, текущее количество строки 8297 не установлено. Склад и CRM не изменялись.

## Как проверить добавление позиции

Используйте **новую тестовую сделку**. Не повторяйте старые неопределённые или partial-операции (в частности, прежнюю попытку по сделке 1313 / заявке 8517).

1. Отправьте боту, заменив `НОМЕР` на номер тестовой сделки:
   **«Добавь в сделку НОМЕР товар DAP, артикул 2430TK1204, бренд DAP, количество 2, цена продажи 500 рублей за штуку».**
   Это искусственная тестовая цена, не рекомендация цены товара.
2. Проверьте черновик: нужная сделка, бренд DAP, артикул 2430TK1204, 2 штуки, по 500 рублей. До подтверждения записи быть не должно. Если бот спрашивает изменение статуса существующей сделки, выберите сохранение статуса.
3. Подтвердите **один раз**. Для нескольких позиций одной команды должно быть одно подтверждение всей пачки.
4. Откройте сделку в STOCRM и сверьте артикул, бренд, количество **2**, цену **500 за штуку**, сумму **1000**, отсутствие дубля. Сообщения «запрос принят» недостаточно — важна фактическая строка в панели.
5. Если бот сообщает `partial`, неопределённый результат или несовпадение цены/количества: **не повторяйте команду и не подтверждайте повторно**. Сначала проверьте сделку и заявку в панели, затем соберите диагностику.

Версия 75 использует `offer/order/add_free_order` как основной метод обычного ручного добавления. Подбор склада и поставщика для него не нужен. После ответа API бот перечитывает строку и проверяет цену/количество; при несовпадении или неоднозначном количестве останавливает пачку без автоматического повторного добавления и без переключения на другой метод.

Неподтверждённый старый ручной черновик со старым маршрутом записи блокируется. Создать новый вместо него можно только если попытки записи ещё не было; `partial` и уже отправленные заявки таким способом обходить нельзя.

## Проверка даты записи — исправление версии 75

Если бот уже знает «сегодня» и спрашивает время, ответы **«11 утра»**, **«11»**, **«в 11»**, **«11:00»** сохраняют выбранную дату и означают 11:00. Чтобы явно поменять день месяца, напишите «11 ноября» или «11 числа».

Проверка на тестовой сделке: «Запиши сделку НОМЕР на сегодня к рыжему» → ответьте на вопрос о статусе → «11 утра» → «час». В черновике должна быть сегодняшняя дата, интервал 11:00–12:00. При включённых подтверждениях до нажатия подтверждения запись не создаётся.

Ранее ошибочно созданная запись №2153 сама не переносилась. Сначала проверьте её текущее состояние в панели; если она всё ещё на неверной дате, исправляйте именно эту запись, не создавая дубль. Обновление меняет понимание новых ответов, а не существующие данные CRM.

## Если возникла проблема

Дважды щёлкните **`collect_report.bat`**. Он не изменяет CRM, создаёт диагностический `support_report.txt` и открывает его в Блокноте. Укажите текст команды, ответ бота и номер тестовой сделки. Перед отправкой просмотрите файл и удалите личные сведения. Не присылайте `.env`, токены, SID или всю `.state`.

В отчёте версия кода должна быть **82**, дата **2026-10-31**. Иначе запущена другая папка или старая копия.
