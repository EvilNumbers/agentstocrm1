## Новая сделка по телефону — версия 94

По снимку бот предложил создание контакта «Новая сделка» вместо использования существующего. Подготовка теперь проверяет номер и показывает существующего клиента; новый контакт предлагается только после законченного поиска и ввода настоящего имени. Несколько совпадений, неполный поиск и несколько воронок требуют выбора. Черновик подтверждается человеком, повторно проверяет номер и воронку перед записью; старые непроверенные черновики создания сделки заблокированы. Применение использует документированный `offer/new/with_contact` с обязательным PHONE и, для существующего клиента, CONTACT_ID (WIKI-A-613), далее проверяет созданную сделку и контакт. Неизвестный результат остаётся partial и не повторяется автоматически.

Проверка дополнительных телефонов ограничена 20 карточками; при неполном поиске отсутствие клиента не утверждается и создание нового блокируется. Тесты на имитации, живая CRM не изменялась; фактическое поведение STOCRM, производительность и полнота поиска на базе пользователя не проверены.

## Подробный локальный ответ Росско — версия 93

По прямой просьбе пользователя при сетевом или серверном сбое GetCheckoutDetails создаётся уникальный текстовый файл рядом с используемым `.env` в `rossko_local_reports`. В нём: HTTP статус и content-type, категория и текст исключения, поля success/message или SOAP Fault и тело ответа до 2 МБ с отметкой об усечении/обрыве; текст запроса и `.env` специально не добавляются, но сервер может вернуть их в теле ответа. Данные остаются локальными и не включаются в обычный support report. Обнаруженные точные ключи и распространённые XML-представления маскируются, но файл всё равно может содержать другие секреты, их фрагменты, персональные данные, адреса или реквизиты. Не отправлять файл целиком без ручной проверки. Стандартная папка исключена в `.gitignore`, также программа пытается создать `.gitignore` внутри папки отчётов; это не защита для иных путей и копий.

На успехе и отмене выбора отчёт не создаётся; при ошибке записи отчёта остаётся краткое сообщение. Запрос по-прежнему фиксированным GetCheckoutDetails, без заказов, перенаправлений и повторов, настройки `.env` и `.state` при сбое не меняются. Настоящее соединение не проверено, тесты на имитациях; отчёт не гарантирует устранения R01/A2.

## Диагностика отказа GetCheckoutDetails — версия 90

По снимку пользователя v89 получил ответ в структуре CheckoutDetailsResult, но status `success` отсутствовал либо его значение было не true/1: старый код объединял эти случаи. Добавлено разделение на явно отрицательный статус (категории R01–R04 по словам в поле message), отсутствие статуса R05 и неожиданное значение R06. Категории являются приблизительными подсказками, а не доказательством причины. Сначала реальные значения ключей исключаются из классифицируемого сообщения; в версии 90 произвольный текст сервера не сохранялся; начиная с версии 93 при ошибке он включается в локальный отчёт. Сетевой запрос и политика отсутствия заказов не изменены; сбой не меняет `.env` или `.state`.

Причина отказа неизвестна, фактический ответ на ПК пользователя не был виден. Проверки только локальные, без реальной CRM и Росско; новое сообщение само по себе не устраняет ошибки учётной записи, доступа или сети. WSDL через инструмент ранее вернул HTTP 500, реальная совместимость wire format не подтверждена.

## Локальный выбор ID Росско — версия 89

По просьбе пользователя добавлен отдельный запуск `Получить_ID_Росско.bat`: только после явного запуска выполняется один запрос чтения GetCheckoutDetails к фиксированному HTTPS endpoint. Существующие локальные ключи не выводятся, WSDL и zeep не требуются. Бот сам данный запрос не запускает; GetCheckout и заказы не реализованы. В ответе Росско могут присутствовать конфиденциальные сведения; способы и совместимые адреса отображаются только локально, не в чат/модель. Начиная с версии 93 ответ с ошибкой сохраняется локально в подробный отчёт и может содержать конфиденциальные поля. Коды и адреса не запрашиваются у пользователя в чате.

Оператор выбирает номер способа и совместимого адреса из ответа либо явно указывает поиск без адреса; не угадываются ID и совместимость. Сохраняются только `ROSSKO_DELIVERY_ID`/`ROSSKO_ADDRESS_ID`, с проверкой изменения `.env` во время запроса, без изменений `.state`. При отмене или сбое запись не выполняется. Окружение имеет приоритет над `.env`, поэтому если `ROSSKO_*` заданы в окружении, мастер ID останавливается. Повторный запуск старого мастера настройки ключей очищает ID; тогда нужно заново выполнить выбор.

Формат ответа основан на официальной документации https://api.rossko.ru/index.php?action=SOAP&path=%2FGetCheckoutDetails ; WSDL через инструмент документации вернул HTTP 500, поэтому реальный wire format и успех на аккаунте не подтверждены. Проверки используют только имитации, без обращений к настоящим Росско и CRM; наличие способа доставки не означает успешный поиск или наличие товара.

Клиент продолжает выполнять не более одного запроса к фиксированному GetSearch, без перенаправлений и операций заказа; данные для других методов, CRM и `.state` не изменялись. Без delivery ID документация не обещает успешный поиск; предупреждение теперь говорит о настройке без ID, а не утверждает, что запрос обязательно дошёл. Причина ошибки на пользовательском ПК и корректность работы реального API не установлены; тесты используют имитации. Найденная в истории CRM позиция не подтверждает результат Росско или наличие.

## Настройка Росско — версия 87

Ввод в локальном мастере заменён на обычный видимый: оператор должен защищать экран и не присылать ключи или `.env`. Подтверждение «ДА» удалено, после ввода ключи сразу сохраняются. Клавиша Enter сохраняет ранее записанный ключ; если ключа нет — запись не начинается. Дубликаты ключей/настроек Росско в `.env` сводятся к одной строке, формат ключей теперь проверяется по возможности точного чтения парсером `.env`, а не по узкому списку символов. Сообщения об ошибках показывают безопасную категорию и, при системной ошибке, номер без пути, содержимого файла или ключей.

Настройка по-прежнему без сетевых запросов, отключает ID для пробного поиска и не меняет `.state`; заказы поставщикам остаются заблокированы. Причина ошибки на ПК пользователя неизвестна; локальные тесты не подтверждают работу на пользовательском Windows или реальном API Росско. Официальная документация указывает ID доставки обязательным, поэтому пробный поиск без ID может не работать.

## Команда добавления клиента — версия 82

По скриншоту «Добавь клиента [телефон]» перехватывался разбором товара и телефон становился артикулом. Явное создание клиента теперь обрабатывается до поиска товаров, независимо от TG_FASTPATH; бот запрашивает недостающее имя или номер и не выдумывает фамилию. Запрос одновременно на создание клиента и запись в сделку требует уточнения. При наличии номера проверяются основной и дополнительные телефоны; совпадения не дублируются, неполный поиск блокирует создание. Ограничение проверки дополнительных телефонов до 20 карточек за проход сохранено, что может препятствовать созданию на больших базах. Список найденных контактов может быть неполным, и результат отрицательного неполного поиска не считается доказательством отсутствия.

Создание использует документированный метод https://stocrm.ru/wiki/article/WIKI-A-631/ . До подтверждения данные перепроверяются; по ответу с ID перечитываются имя и телефон. ## Пакетный подбор товаров — версия 78

На MockSession воспроизведён сценарий с двумя неизвестными артикулами: после ручного выбора первого старый pipeline отдавал одновременно вопрос по следующему и черновик первой позиции. Telegram callback показывал кнопку подтверждения неполной заявки. Исправлено отдельной последовательной сборкой нескольких ручных позиций: сначала только чтение/ответы, без черновиков и записи; после выбора, пропуска или ввода цены для каждой позиции — один объединённый черновик. При отключённом подтверждении вся проверенная очередь запускается только после завершения вопросов. Старые кнопки выбора отклоняются, параллельные ответы сериализованы. Заготовки в момент создания/объединения заблокированы от применения, в том числе после прерывания процесса. Явные закупочные поля и поставщик в пакете не отбрасываются: бот пока предлагает отправить такие позиции отдельно.

При расхождении фактических цены/количества или невозможности привязать прочитанную строку к сделке и возвращённому ID результат partial, оставшиеся позиции не отправляются, повтор блокируется. Автоматические попытки коррекции цены/количества после readback удалены. Новая просьба или ранее подготовленный черновик с тем же артикулом в той же сделке блокируется, даже если изменён бренд; скрытие partial из списка не снимает блокировку. Непроверенные старые результаты с предупреждением также сохраняются. Подтверждение через повторную проверку требует ID созданной строки; неподтверждённые и ещё не отправленные позиции не считаются выполненными. Ранее по снимку версии 75 текст успеха соседствовал с предупреждением; в базе версии 77 форматирование с предупреждением уже не выводит заголовок успеха. Для успешно проверенного пакета показывается число подтверждённых позиций. По уточнению пользователя 1 000 000 относится к остатку виртуального склада; количество строки сделки неизвестно. Сделка 1313, строка 8297 и заявка 8517 не изменялись, фактическое состояние неизвестно; не повторять.

Для набора до четырёх не найденных в CRM артикулов используется один объединённый запрос одного выбранного провайдера (DDG/Searx — без запасного адреса в этом режиме), затем результаты сопоставляются по каждому точному артикулу отдельно. Фрагменты с несколькими артикулами не используются для установления бренда. Допускается ранее неизвестный латинский бренд рядом с артикулом или явно подписанный бренд; интернет-варианты требуют выбора человека и показывают источник. Сортировка учитывает количество источников. Кэш, single-flight, ограничение частоты и пауза после CAPTCHA/429 сохранены; если поиск не завершился, это не является доказательством отсутствия позиции. Выдача не обязана покрывать всю группу. Проверка сетевого маршрута и прочие одиночные функции могут выполнять отдельные запросы. Интернет-сайты не подтверждают применяемость или наличие в CRM.

Локальные проверки: **88 pytest**, в том числе **26 новых** тестов пакетного диалога и mock Telegram Dispatcher: два выбора и единая кнопка, авто-режим, пропуск/отмена, неизвестная сделка и цена, 5 позиций двумя запросами, несколько брендов и запрет перекрёстного сопоставления, кэш и пауза 429, отсутствие обхода ограничений в DDG/Searx, точные payload, readback, отсутствие ID или сделки, расхождение количества и остановка без записи следующей позиции, блокировка незавершённого черновика. MockSession и фальшивая Telegram-сессия не являются реальной CRM/Telegram. Ruff F,B,SIM,RET,PIE,E9, mypy (41 файл), compileall и CLI --help прошли. ## Запись клиента по телефону — версия 77

Локально воспроизведена первопричина снимка: телефон без слова «телефон» не попадал в аргументы, а после отмены предыдущая сделка оставалась в контексте и подставлялась в новую просьбу. Теперь просьба с телефоном проходит отдельный путь: поиск контакта с проверкой основного и дополнительных телефонов (форматы российского номера с 8 и +7 сопоставляются), затем полный ограниченный постраничный поиск сделок с локальной проверкой CONTACT_ID. Если телефон принадлежит нескольким контактам, выбирает человек. Если контакта нет, уточняется имя и готовится создание контакта и новой сделки.

Активны все статусы, кроме «Успешно реализовано», «Отказ», «Мусор», «Возврат». При активных сделках предлагается создать новую или выбрать конкретную существующую. Статус существующей сделки автоматически не меняется; данные времени и мастера сохраняются, одного общего подтверждения достаточно. Ограничение интерфейса: при более чем 30 активных сделках требуется указать номер нужной сделки вместе с телефоном; бот не выбирает сам.

В случае неполного или ошибочного чтения, повторяющихся страниц, отсутствия связи с клиентом или неизвестного статуса запись не начинается. Перед отправкой перечитываются контакт, активные сделки и календарь; изменившиеся данные блокируют применение. Незавершённые/неопределённые календарные попытки по клиенту или сделке блокируют повтор, в том числе новым запросом. Старые черновики записи, подготовленные до этой проверки, блокируются; неподтверждённый и ещё не отправленный можно отменить и подготовить заново. Partial таким образом обходить нельзя. Полную атомарность с изменениями в панели после последней проверки API обеспечить нельзя.

## Цветные статусы сделок — версия 76

## Сохранённое исправление добавления позиции (версия 74)

Основной маршрут обычной ручной позиции (source=manual) теперь **offer/order/add_free_order**, а не offer/order/add. Это смена основного метода, не запасная попытка после неясного результата.

Передаются REQUIRE_ID, NAME, BRAND, SKU, PRICE (цена продажи), NEED_MARKUP=False, AMOUNT и CURRENT_VOLUME (заданное количество), MIN_VOLUME=1. Не выполняются выбор поставщика, поиск складской позиции или подбор технического склада. Если явно переданы закупочные поля, manual отклоняет их до записи, а не теряет молча. Ранее для source=supplier использовался offer/order/add; с версии 85 этот путь заблокирован.

Одна команда с несколькими позициями — один черновик и одно подтверждение. Проверяются согласованность карточки/параметров перед записью, факт строки, её цена и количество после записи. Несовпадение, пустой/непонятный ответ и неопределённый результат не превращаются в успешный ответ. Native не выполняет fallback, перебор полей или автоматическое повторное добавление. ## Ограничение, которое важно учитывать

Доступа к реальной CRM пользователя нет, поэтому реальный вызов и правильное отображение результата в его панели **не подтверждены**. Поля количества native взяты из рабочего исходника; официальная гарантия их поведения не установлена. Именно поэтому нельзя объявлять успех по одному ответу API: включена последующая проверка фактической строки и безопасная остановка при несовпадении.

Старая ошибка order/add с пустым ответом не объявляется исправленной изменением UID. Вместо этого для новых ручных позиций выбран другой основной маршрут. Старую неопределённую попытку по сделке 1313 / заявке 8517 повторять нельзя.

## Запуск и приёмка

Подробные шаги — в README.md. Кратко: остановить старую копию → распаковать новую папку → сохранить/перенести собственные .env и .state → setup.bat → start_bot.bat. Приёмка на новой тестовой сделке: DAP 2430TK1204, 2 штуки по тестовой цене 500 рублей; сверить панель (сумма 1000, нет дубля). При partial не повторять, собрать collect_report.bat.

Сохранены подтверждения человеком (отключение только через /settings), запрет внесения оплаты и назначения исполнителя услуге, отсутствие автоматической смены статуса существующей сделки, отсутствие подбора складского товара для обычной ручной позиции.
